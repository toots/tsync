# Adversarial review of the rewrite, 2026-10-01

Branch `rewrite`, at a9ccd733. Ten reviewers each took a share of the docs/pitfalls/ themes (A-1 to A-12, B-1 to B-12, C-1 to C-10), plus the runtime (vendor/duppy, lib/core/rt.ml) and the C stubs. Each one used every entry's **Check** line as a question to put to the code, then looked for variants of the same mechanism. The review was read-only. Several findings were reproduced on scratch copies of the tree, and the GCS and S3 findings come from CI logs.

The reviewers reported 186 raw findings. Merging those with the same root cause leaves **159**: 6 critical, 30 high, 71 medium and 52 low. Where reviewers disagreed on severity, the decision and its reason are noted. "Found by N" counts the reviewers (R1–R10) who reported the finding independently. Four findings were re-checked directly by the lead and are marked "verified by lead". The other three criticals were re-opened against the code before being kept at critical.

Reviewer areas: R1 durability, R2 concurrency and runtime, R3 namespace and journal, R4 failures and liveness, R5 stores and GC, R6 caches and ownership, R7 security and syscalls, R8 and R9 resources, R10 build and tests.

## Fix first

### Critical

1. **Start-up recovery deletes the staged bodies of an undecodable staged manifest**
   - Status: Fixed in `6596dad7`.
   - Severity: critical. Confidence: confirmed, verified by lead. Found by 1 (R4). R1 had listed A-1.16 as checked clean.
   - Where: lib/sync/engine.ml:1221-1223 (`Fs.rename p (pick 1)` comes first, then `Fs.read_file_opt p` reads the old name), engine.ml:1230-1240 (orphan sweep).
   - Scenario: `recover_local` sets aside a staged manifest that does not decode, then reads it back under its old name. The read answers `None`, so `named` gets none of its bodies, and the orphan sweep `Fs.release`s them. The only copy of the user's unpublished bytes is deleted on the start that set the manifest aside.
   - Fix direction: read the body before the rename, or read it from the set-aside name. If that read fails, skip the orphan sweep on that start.
   - Pitfalls: A-1.16, A-4.1, A-4.16.

2. **An upload or file rename overwrites a peer's folder marker**
   - Status: Fixed in `58746026`.
   - Severity: critical. Confidence: confirmed, verified by lead. Found by 1 (R3).
   - Where: lib/sync/outbound.ml:127-139 (`store_record` gives `` `Record (Manifest.decode b) ``, which is `None` for a marker), outbound.ml:723-728, :806; lib/remote/remote.ml:260-261 (`R.publish` is a plain put to the slot), remote.ml:270-275 and outbound.ml:422-424 (a file rename copies over the slot).
   - Scenario: B publishes `mkdir x`. Before A applies it, A creates and closes a file `x`. The marker decodes as "no manifest", so the upload counts as P1 and puts A's manifest over B's marker. B's folder and its whole subtree become unreachable, and A19's later aside deletes the slot for good. The same happens through a local rename onto `x`, republish-here and revive-ours.
   - Fix direction: classify the slot as none, file record or folder marker (`Tree.classify_slot` already does this). A marker at the slot means `store_moved_on` or `destination_taken`. Never put a manifest over a marker.
   - Pitfalls: A-3.1, A-3.14.

3. **One malformed chunk key makes a manifest reference nothing, so GC deletes every chunk of the file**
   - Status: Fixed in `c2f49dff`.
   - Severity: critical. Confidence: confirmed, verified by lead. Found by 1 (R5).
   - Where: lib/core/manifest.ml:73 (`try keys m with _ -> []`), lib/store/chunk_spaces.ml:109-119 (`references`), :121-144 (`gate`), lib/gc/collector.ml:98-114.
   - Scenario: bit rot changes one hex digit in a manifest's key. `chunk_names` swallows the CORRUPT and returns `[]`. Marking then promotes none of the file's N chunks, and closing deletes them on the main and on every copy. The gate also publishes such a body without checking that its chunks are present.
   - Fix direction: `references` returns `Error` when any key fails to decode. The collector halts with the run left open (gc.md §5.5), and the gate refuses the body as invalid.
   - Pitfalls: A-7.4, A-7.7.

4. **A local rename leaves the source path's upload live: the old name comes back and the renamed file is corrupted**
   - Status: Fixed in `5967e17c`.
   - Severity: critical. R2 rated it high; R1 reproduced the corruption of a user file through the ordinary editor save pattern (write a temp file, then rename it). Confidence: confirmed (R1 repro4.ml). Found by 3 (R1, R2, R3).
   - Where: lib/sync/local_ops.ml:1027-1050 (`rename_local`), :1083-1100 (`rename`), :1022-1026 (`repost_moved` posts the new keys and never cancels the old); lib/sync/outbound.ml:802-811 (commit guard), local_ops.ml:1193 (`promote` → `release_unnamed`); also engine.ml:217 and :301 (`Staged.move` with no bump).
   - Re-checked: `rename_local` calls `Staged.move staged ~src ~dst` without `bump src`, and the commit's only guard is `if generation path <> g || Atomic.get cancel then raise Rt.Cancelled`. Nothing changes either value for the source key.
   - Scenario (in flight): the upload of `a` commits after `mv a b`. It publishes `a`, writes a Committed staged edit back at `a`, and `promote` releases the bodies that `b`'s moved edit still names. Locally `b` reads as CORRUPT, and every peer gets a phantom `a`.
   - Scenario (pending): an upload queued for `notes/a.txt` runs after `notes` was renamed. It finds no staged edit there, resolves `notes` through its removed-id record, installs the old manifest at `notes/a.txt` (recreating an id-less `notes/`) and publishes a Put.
   - Fix direction: every move of a staged edit (rename, aside, rescue) bumps the source key and cancels its upload in the same step that posts the new key. The commit re-reads the staged edit under the key lock and aborts unless it is the edit it uploaded. An upload that finds no staged edit and no mirror entry owes nothing.
   - Pitfalls: A-1.4, A-1.5, A-1.6, A-1.13, A-2.3, A-2.4, A-3.17.

5. **A conflict aside of a partial edit can never be read or published**
   - Status: Fixed in `5967e17c`.
   - Severity: critical. R1 rated it high; R6 rated it critical. Critical because the conflicted copy exists to preserve the edit, and the edit becomes unrecoverable once GC collects the base chunks that nothing roots. Confidence: confirmed (R1 repro.ml). Found by 2 (R1, R6).
   - Where: lib/checkout/staged.ml:266-276; lib/sync/local_ops.ml:379-397 and :582-596 (`base_of path`); lib/sync/outbound.ml:726-733 and :766-778; lib/sync/engine.ml:215-217 (`file_aside`).
   - Re-checked: `Staged.move ~new_file:true` keeps the `Slots` and sets `base = (if new_file then Base_none else e.base)`. `Inherit` slots are then resolved through `base_of path`, the mirror entry at the edit's *current* path, which ends in `Fail.corrupt "%s: chunk %d inherits from a base that lacks it"`.
   - Scenario: A edits a published file in place, so most slots stay `Inherit`. B publishes the same file first. A's edit is moved to `f (conflicted copy from A)`, which has no mirror entry. Reading the copy fails CORRUPT, and its upload parks with the same error. A rebuild that rewrites the mirror under an in-place edit makes `Inherit` read B's chunks instead of A's base.
   - Fix direction: resolve `Inherit` against the edit's recorded base, keeping the base manifest with the staged edit. Alternatively, materialise the inherited slots into staged bodies before any move that drops the base.
   - Pitfalls: A-1.7, A-1.19, A-8.8.

6. **Any route's secret can write a share manifest through `copy` and serve another domain**
   - Status: Fixed in `48be2787`.
   - Severity: critical (security; the attacker's client is any HTTP client, and the server is in the tree). Confidence: confirmed by trace. Found by 1 (R7).
   - Where: lib/frontends/http_proxy/store_server.ml:348-382 (`share_candidates`), :272-276, :600-603, :469-471 (`writable`), :924-952.
   - Re-checked: a copy carries two names, so `share_candidates` falls through to `| _ -> t.routes`. The executor then runs only `writable route dst`, which exempts `Key.under Key.shares k`. The §6.4 check that the manifest's domain equals the route's domain never runs.
   - Scenario: domains A and B share a bucket and one listener. A holder of A's secret puts a share manifest naming B under `shares/cache/x`, then copies it to `shares/<token>`, and `GET /s/<token>` serves B's root folder. Copying onto an existing B token instead hijacks or kills B's link, and copying a manifest out to `cache/y` reads any manifest whose token is known.
   - Fix direction: treat a copy whose `dst` (or `src`) is a manifest name as a manifest write, and apply the domain check to the source body. Simpler still, refuse a copy into or out of manifest names. Refuse share-space writes that are neither a manifest nor under `cache/`.
   - Pitfalls: A-9.1, A-9.4.

7. **The journal poller dies on the first failed pass, and the publish gate stays closed**
   - Status: Fixed in `272c84f6`.
   - Severity: high. Confidence: confirmed. Found by 2 (R3, R4).
   - Where: lib/sync/engine.ml:1024-1040 (`apply_pass` runs in the value arm of `match Journal.cursor_token … with exception`), engine.ml:772-776, lib/sync/outbound.ml:25-54.

21. **The scheduler exits the process when two cancelled waits outlive their descriptor**

22. **Waiting on a closed descriptor leaves `tasks_m` locked, and the whole runtime wedges**

25. **Settle turns G even while a run sits suspended in Closing**
   - Status: Fixed in `cb650c5f`.
    - Severity: high. Confidence: confirmed by trace (no test). Found by 1 (R5).

28. **IPC client `connect` has no deadline and pins a scheduler thread once the peer's backlog is full**

## Clusters

- **Background fibers die silently.** An exception that escapes a loop body ends the fiber with one log line, and nothing restarts it or reports the stall: the poller (7), queue workers (8), the watch gate (124), the probe (50). Guard every loop body so that only Stopping ends it, and add the per-queue watchdog (43).
- **Moving local state leaves the old key's work live.** Rename, aside, rescue, arrival moves and retargets each move a staged edit without bumping the source key, cancelling its upload, or re-posting at the new key (4, 5, 12, 38). One `move_edit` primitive that bumps, cancels and re-posts, and that resolves `Inherit` against the edit's own base, fixes all of them.
- **Decisions re-made against stale or partial facts.** An EXECUTED record is re-decided (10), P22 retries the in-memory record (11), `Unresolved` is folded into absent (16), a marker decodes as "no manifest" (2), a malformed key reads as "no references" (3), and the batch read answers absent for keys it never read (26). "Could not tell" must be a distinct answer that blocks the decision, never a default.
- **Rebuild races local work.** The walk and sweep run for minutes against a mount that stays writable, and they trust a check made before the walk (13, 14, 38, 40). Either freeze namespace mutation and promotion for the sweep, or have the sweep skip everything touched since `t0`.
- **Cancellation does not clean up.** Cancelled children outlive `Rt.first` (47), waiters stay registered (48, 21), contexts leak (49), and fds leak between socket creation and hand-off (55). Cancellation must deregister and join, and resource cleanup must run after the losers are done.
- **Unbounded per-item tables and whole-set passes.** These include `klocks`, `gstate`, the dedup and copy memos, the applied log and the GC referenced set, along with whole listings and quadratic lists in the queues, staged walks and mirror (54, 68-71, 77, 82-85, 90-93). Each table needs an eviction rule and each pass a page size, sized against the Pi rather than the dev box.

## Spec gaps

Places where the code follows the spec and the spec is wrong:

- **01 §10 vs uplink-governor A2 (finding 23).** 01 counts request-body chunks as progress, while A2 says request-side progress does not reset the timer. The code follows A2 by omission. Amend A2.
- **conflict-resolution P13 and the wal-and-journal crash table (finding 10).** They read `already_trashed` as "already published", which does not hold for rmdir: the trash move precedes the journal put. Make P13 publish the entry when the record holds one.
- **replication §4.8 settle condition (finding 25).** "G odd and nothing owed" ignores a run suspended in Closing, against gc.md §5.5's intent. Add "no run record in Closing at g".
- **gc.md run lock described as "a POSIX record lock" (finding 24).** Process-wide release on any close makes this unsound once the same file is opened for another lock. Specify an OFD or `flock` lock on a dedicated file.
- **http-proxy §8.1 memoises 401 (finding 27).** It must exclude a 401 whose `Date` shows clock skew.
- **04 §4.5 symlink step order (finding 45).** The mirror write precedes the owed record. Record first.
- **backends/local.md declares `fast_read` unconditionally (finding 148).** It should be false on a network filesystem.
- **data-model/backend.md `landedAt` wall time (finding 140).** Claim settle needs a monotonic in-process bound as well.
- gc §5.9 permits live-set memory for the dry run (finding 82). That is acceptable for the spec but not for an owner on the Pi: run the survey out of process or spill it.
